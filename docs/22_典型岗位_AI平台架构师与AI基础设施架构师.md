# 典型岗位与面试：AI 平台架构师 / AI 基础设施架构师

> **岗位方向**：AI Platform / Agent Infrastructure / Cloud Native / GPU Infrastructure
> **经验要求**：8 年以上开发/架构经验，3 年以上 AI 相关项目经验优先
>
> 本章与第 19 章（大模型推理服务可靠性工程师）是**同一岗位族的两端**：第 19 章考"把一条推理链路做稳"，本章考"把整条技术栈搭起来并长期演进"。建议先读第 19 章。

## 1. 岗位定位（一句话拆解）

JD 的核心要求写得很清楚：要能完成从

```
AI 应用 → Agent → 模型服务 → GPU 算力 → Kubernetes → DevOps → 可观测性
```

的**完整技术架构设计**。

把它翻译成三条主线：

| 主线 | 要解决的问题 | 交付物 |
|---|---|---|
| **平台化** | 各业务各接各的模型、各写各的 Agent，重复造轮子、无法治理 | 统一 AI Gateway、统一模型调用层、Agent/Tool Runtime、版本与发布体系 |
| **工程化** | 平台能上线但改不动、回不去、查不到 | Python/Go 双栈、K8s 多集群、CI/CD + GitOps、五类版本追踪 |
| **算力化** | GPU 很贵，利用率低、冷启动慢、成本不可控 | GPU 资源池与调度、推理优化、显存与 OOM 治理、成本核算 |
| **稳定性** | 出问题定位不到、容量拍脑袋 | Metrics+Logs+Traces+Alerts 四件套 + AI 业务指标 + 容量模型 |

**与"工程师"回答的最大区别**：架构师要能说清 **为什么这样选、边界在哪、代价是什么、怎么退、怎么演**。见第 5 节。

## 5. 架构师岗位的答题差异（重要）

同样一个问题，工程师和架构师的答案长度可以一样，但**结构不同**：

| 维度 | 工程师答 | 架构师答 |
|---|---|---|
| 起点 | "我用 XX 实现" | "先看约束：QPS、SLO、预算、团队规模、合规" |
| 结构 | 组件清单 | 分层 + 数据流 + 边界 |
| 关键 | 功能能跑 | **取舍**（为什么要，为什么不要） |
| 风险 | 出问题再修 | 失败模式、爆炸半径、降级与回滚 |
| 度量 | 功能验收 | SLO、成本、成功率、水位 |
| 收尾 | 交付即结束 | 演进路径与下一阶段 |

**推荐回答模板（背下来）**：

```
目标 → 约束 → 方案（分层图） → 关键取舍 → 失败模式与兜底 → 度量指标 → 演进路径
```

## 6. 模拟面试问答（33 题）

> 加 ★ 为高频必考。建议先自己答一遍，再对照补齐。

### A. AI 平台架构

**★Q1. 设计一个统一 AI Gateway，要同时对接 OpenAI、Claude、Gemini、DeepSeek、Qwen、MiniMax 以及私有部署模型，你怎么设计？**

- **参考回答**：分四层。①**接入层**：只暴露一套对内协议（建议 OpenAI 兼容，因为生态最广），把"供应商差异"关在门内；②**适配层**：每个供应商一个 Adapter，负责鉴权、请求/响应字段映射、流式事件格式统一、错误码归一（把各家的 rate limit / content filter / context length 错误映射成统一错误码）；③**策略层**：路由、Fallback、负载均衡、限流、熔断、重试、预算与配额都在这里，**不要散落到业务代码**；④**控制面**：模型清单、密钥、配额、路由规则的配置与灰度。关键设计点：**流式（SSE）必须端到端打通**，中间任何一层缓冲都会毁掉 TTFT 体验；**幂等**要先做（同一次请求带 request id，重试不产生重复计费/副作用）；**可观测**要按"供应商 / 模型 / 业务 / 租户"四个维度打点，否则成本算不清。最后明确边界：Gateway **不做业务逻辑**，只做协议归一与策略执行。

**★Q2. 路由、Fallback、负载均衡、限流、熔断、重试、成本控制，怎么在一层里做出来？重试为什么危险？**

- **参考回答**：按"决策顺序"串起来：①**鉴权与配额**（超预算直接拒绝，不要等到调用后才发现）；②**路由**：先按能力过滤（是否支持 tool calling / 长上下文 / 多模态），再按策略排序（成本优先 / 延迟优先 / 质量优先 / 粘性会话）；③**限流**：令牌桶按租户+模型双维度，避免一个业务打爆全局；④**熔断**：按供应商/模型/endpoint 维度统计错误率与 P99，熔断后半开探测；⑤**Fallback 链**：主模型 → 备用模型 → 降级模型（如小模型/缓存答案/明确报错）；⑥**重试**：只对**幂等且可重试**的错误重试（连接失败、5xx、超时），且必须**指数退避 + 抖动 + 重试预算**，禁止对 4xx、内容审核、参数错误重试。
- **重试为什么危险**：重试会把局部故障放大成全局雪崩——一个模型变慢 → 上游超时 → 全体重试 → 流量翻数倍 → 把还没挂的供应商也打挂。这是分布式系统的经典陷阱（"Retry is dangerous, fail fast is underrated"，见第 20 章）。所以要有**重试预算（retry budget）**和**熔断兜底**，并在链路里禁止"每层各重试一次"的乘法放大。实践中推荐：**重试只在一处做（Gateway），下游不再重试**。

**Q3. 成本控制具体怎么做？**

- **参考回答**：四个抓手。①**可见**：按租户/业务/模型/接口打点 token 与费用，做到"谁花的钱能查到"；②**可管**：配额 + 预算 + 告警，超限自动降级（换便宜模型/限制并发/排队）；③**可省**：前缀缓存（相同 system prompt 复用）、结果缓存、Prompt 压缩、上下文裁剪、小模型前置分流、批处理合并、量化（FP8/INT8）；④**可算**：建立**单位成本指标**（每千 token 成本、每张图成本、每个 Agent 任务成本），把它和 SLO 一起放进发布门禁——成本劣化超过阈值就不许发布。补充一句架构判断：**成本优化最有效的往往不是"换更便宜的模型"，而是"减少无效调用"**（缓存、去重、更好的路由）。

**★Q4. Agent Runtime / Tool Runtime 怎么设计？**

- **参考回答**：把 Agent 当成一种"需要被托管的工作负载"，Runtime 提供六件事：①**工具注册中心**：工具名、版本、JSON Schema、风险等级、所需权限；②**权限与审批**：读操作可直接执行，写操作/高风险操作走审批（三态：允许 / 拒绝 / 挑战）；③**沙箱执行**：代码执行、Shell、网络访问都要隔离并限制资源与时长；④**状态与恢复**：每一步落盘（操作意图、工具调用、结果），失败可从最近可信状态恢复（WAL / Checkpoint 思路，见第 20 章）；⑤**预算与停止条件**：最大步数、最大时长、最大 token、最大成本，缺一不可，否则会无限循环烧钱；⑥**可观测**：完整轨迹（trajectory）可回放，这是后期定位"为什么这次答错了"的唯一手段。工具协议上，**MCP 已是事实标准**，把它做进 Runtime 比让每个业务自己接要划算得多。

**★Q5. 模型、Prompt、Agent、Workflow 的版本管理与发布体系怎么建？**

- **参考回答**：核心认知是——**这四类资产的"代码"不是代码，但它们必须和代码一样可版本化、可灰度、可回滚**。做法：①**统一资产模型**：每类资产有 `id + version + 状态（draft/canary/stable/deprecated）+ 关联关系`；②**评测门禁**：任何变更先跑离线评测集（Golden Set + 边界 + 对抗），指标不劣化才允许进入灰度；③**灰度与流量切分**：按租户/业务/百分比切流，观察线上指标；④**一键回滚**：旧版本必须保持**可即时切换**（这也是为什么推理侧要保留旧模型的热实例，否则回滚要等几十 GB 权重加载）；⑤**发布记录可追溯**：这次线上用的是哪个模型版本 + 哪个 Prompt 版本 + 哪次 Workflow 变更，必须能在一次查询里拿到。**特别注意**：Prompt 和模型不能走"普通的代码发布"—代码发布是"原子替换"，而模型可能有几十 GB 的热加载与缓存，二者的回滚时间和风险完全不同。

**Q6. AI 服务的高可用、高并发、可扩展怎么做？**

- **参考回答**：先认清一个特殊点——**模型服务是"有状态的稀缺资源"**：副本冷启动要几十秒到几分钟，显存是硬约束，一个副本的容量随输入长度剧烈变化。所以：①**无状态前置 + 有状态后置**：网关/编排层无状态可随意扩，模型层按副本池管理；②**容量按"最长上下文的最坏情况"算**，按 P95 峰值加冗余，不能按平均值；③**多副本 + 反亲和 + PDB**，避免单节点/单可用区故障导致整体不可用；④**过载保护优先于扩容**：先限流、排队、降级（缩短上下文/换小模型），因为扩容来不及；⑤**预热池**：保留一定比例的热实例，应对突发；⑥**可扩展性**要"按维度"设计：加副本（吞吐）、加卡（单请求能力）、加池（隔离不同负载）——三者代价完全不同。

### B. Python / Go 后端架构

**★Q7. 为什么 AI 平台普遍是 Python + Go 双栈？各放哪一层？**

- **参考回答**：因为两类工作的**最优解不同**。Python 的优势是 AI 生态（模型、SDK、数据处理、评测框架全在 Python）和开发效率，适合**业务编排、Agent 逻辑、数据处理、评测**；但 Python 在高并发长连接代理、内存占用、单二进制交付上吃亏。Go 的优势是**高并发、低内存、静态编译、部署简单**，适合**AI Gateway、流式代理、Sidecar、Controller/Operator、任务调度器**。所以典型分工是：**Go 写"入口和基础设施"，Python 写"AI 能力和业务"**，两者之间用 gRPC 或 HTTP 明确契约。反过来做的代价：用 Python 写网关，QPS 上来后 CPU 与内存先崩；用 Go 写 Agent 编排，AI 生态要重新造轮子。补充一个务实建议：**不要为了"技术统一"强行单栈**，但也不要让两种语言随意渗透——边界要写进架构文档。

**Q8. FastAPI + AsyncIO 的常见坑有哪些？**

- **参考回答**：①**在 async 函数里写同步阻塞代码**（`requests`、同步 DB 驱动、`time.sleep`、CPU 密集计算）→ 阻塞整个事件循环；必须换成 `httpx`/异步驱动，或用 `run_in_executor`/线程池隔离；②**CPU 密集任务**（分词、图像处理）应放独立 Worker，别放在 API 进程；③**连接池与超时没设**：默认连接池太小会成为瓶颈，且**必须设 connect/read/total 三类超时**，否则会无限挂住；④**`async` 里捕获异常不严**：取消（CancelledError）被吞掉会导致资源泄漏；⑤**流式响应**要正确处理客户端断开与上游取消；⑥**GIL**：多进程（uvicorn workers）而不是多线程来吃满多核。⑦**Pydantic** 的校验要"边界做一次"，不要在内部反复校验拖慢热路径。

**★Q9. 怎么给 AI 长任务和 GPU 任务设计异步任务系统？**

- **参考回答**：核心是**把"HTTP 生命周期"和"任务生命周期"解耦**。设计要点：①**任务状态机**：`PENDING → QUEUED → RUNNING → SUCCEEDED / FAILED / CANCELLED / TIMEOUT`，状态变更全部持久化；②**提交即返回**：`POST /tasks` 返回 `task_id`，客户端用 SSE/WebSocket 订阅进度或轮询；③**队列分区**：按资源类型（CPU 任务 / 单卡任务 / 多卡任务 / 图像视频任务）分队列，避免大任务堵死小任务；④**幂等键**：同一业务请求重复提交只产生一个任务；⑤**超时与取消**：必须能主动 kill 掉 GPU 任务并**回收显存**，否则会泄漏；⑥**失败分类**：可重试（基础设施抖动）vs 不可重试（参数错误、内容违规）要分开，避免"重试到天荒地老"；⑦**结果落地**：大产物写对象存储，任务表只存引用；⑧**可观测**：队列长度、排队时长、执行时长、失败率——这四个指标就是容量规划的输入。

**★Q10. 高并发下限流、熔断、降级、幂等、重试、分布式锁怎么落地？**

- **参考回答**：
  - **限流**：多维度（全局 / 租户 / 接口 / 模型），令牌桶 + 并发数双控；拒绝要**快速且带可读原因**。
  - **熔断**：按依赖维度（供应商、模型、下游服务）统计错误率与延迟，达到阈值断开并半开探测。
  - **降级**：**提前设计好降级等级**（L0 完整 / L1 缩短上下文 / L2 换小模型 / L3 只返回缓存或明确失败），不要等故障时临时想。
  - **幂等**：写操作带业务幂等键 + 唯一约束，服务端去重；对 AI 场景，`request_id` 同时用于去重与计费对账。
  - **重试**：只在一处重试、只对可重试错误、指数退避 + 抖动 + 重试预算。
  - **分布式锁**：优先用"幂等 + 唯一约束"替代锁；必须加锁时用带 TTL 的租约锁（如 Redis）并做**锁续期与丢失检测**，绝不用"检查再设置"的非原子实现。
  - 一句话原则：**这些机制的目标不是"不出错"，而是"错误不扩散"**。

**Q11. REST / WebSocket / SSE / gRPC 分别用在哪？**

- **参考回答**：**REST** 用于控制面（增删改查、配置、任务提交），简单、可缓存、易调试；**SSE** 用于 LLM 流式输出和任务进度推送——单向、基于 HTTP、穿过代理最友好，是 AIGC 场景默认选择；**WebSocket** 用于真正双向、低延迟的交互（协同编辑、语音对话、需要客户端实时打断的场景），代价是需要处理心跳、重连与状态恢复；**gRPC** 用于服务内部高频调用（网关↔模型服务、Runtime↔工具），优势是 IDL 契约、二进制高效、天然支持流。**架构上的常见错误**：用 REST 轮询做流式（浪费且体验差）、用 WebSocket 承载本该单向的进度推送（复杂化）、内部服务间用 JSON 而不是 gRPC（性能与契约都差）。

### C. Kubernetes / 云原生

**★Q12. 多 Namespace / 多环境 / 多集群部署架构怎么设计？**

- **参考回答**：三个维度分开设计。①**Namespace 维度**：按"环境 + 团队 + 关键业务"划分，配 ResourceQuota + LimitRange + NetworkPolicy，让一个团队打爆邻居变成不可能；②**环境维度**：Dev/Test/Staging/Prod 用**独立集群或至少独立节点池**，同一份镜像通过 values 覆盖差异；配置与密钥走独立管理（Secrets/外部 KMS），禁止把生产密钥放进测试环境；③**集群维度**：按地域（延迟/合规）、资源类型（GPU 集群 vs 通用集群）、爆炸半径（核心与边缘）划分；多集群需要一个**统一控制面**（GitOps + 多集群发布 + 统一可观测）。
- 关键取舍：**多集群能降低爆炸半径，但显著提高运维与网络复杂度**。判断标准是"故障域要求 + 合规要求 + 团队规模"，不是"越多越先进"。GPU 集群还多一层：**卡型与互联不同的节点要分池**，否则 Job 会调度到不该去的地方。

**★Q13. Pod Pending / OOMKilled / CrashLoopBackOff / MinimumReplicasUnavailable 怎么排查？**

- **参考回答**：
  - **Pending**：`kubectl describe pod` 看 Events。常见原因——资源不足（GPU/CPU/内存无节点可满足）、节点选择器或亲和性不匹配、Taint 未容忍、PVC 未绑定、超出 ResourceQuota、镜像拉取中。
  - **OOMKilled**：`kubectl describe` 看 `Last State: Terminated, Reason: OOMKilled`；注意**区分容器内存 OOM 与 GPU 显存 OOM**——前者调 `limits` 或查内存泄漏，后者要看 batch/上下文长度/显存碎片。**不要用"调大 limits"当唯一手段**。
  - **CrashLoopBackOff**：看 `kubectl logs --previous`，常见是启动配置错误、依赖不可达、挂载失败、权限问题（非 root 写目录）、启动探针过于激进。
  - **MinimumReplicasUnavailable**：滚动更新时新 Pod 起不来导致的"卡住"。要查**就绪探针是否可通过**（推理服务常见：模型还没加载完就被判就绪失败）、资源是否够、PDB 是否阻塞了驱逐。
  - 通用方法：**先看 Events → 再看 previous 日志 → 最后进容器手工复现**，80% 的问题在前两步解决。

**★Q14. GPU 在 K8s 上怎么调度？**

- **参考回答**：分五层说。①**暴露**：NVIDIA Device Plugin（或 DRA：Dynamic Resource Allocation）把 GPU 作为可分配资源上报，配合 GPU Operator 统一管理驱动、Container Toolkit、DCGM、MIG；②**申请**：`resources.limits: nvidia.com/gpu: N`，GPU 是**整卡不可压缩**资源（除非用 MIG/时间分片）；③**选址**：NodeSelector/NodeAffinity 按卡型与机房选节点，Taint/Toleration 让 GPU 节点只接 GPU 工作负载，**卡型不同必须分池**（A100/H100/国产卡不能混调度）；④**拓扑**：跨卡通信要求同一 NVLink 域或同 rail 网络，必要时用拓扑感知调度（NCCL 拓扑、NUMA、rail 对齐），否则 TP/EP 性能会断崖；⑤**回收与治理**：配额（Kueue）、优先级与抢占、队列，以及"GPU 不被业务 Pod 空占"的巡检。
- 补充两个易忽略点：**MIG/共享 GPU 适合小模型与开发环境，不适合大模型推理**（显存与带宽隔离不足）；**GPU 节点不能当普通节点用**，把非 GPU 负载调度上去是常见的资源浪费源。

**Q15. Helm 和 Kustomize 怎么选？**

- **参考回答**：不是二选一，常见组合是**Helm 管"打包与版本"，Kustomize 管"环境差异"**。Helm 的优势是模板化、依赖管理、版本化发布（`helm rollback`），适合做"产品化交付物"（把一套 AI 平台做成 Chart 给别人装）；Kustomize 的优势是无模板、纯 YAML overlay、与 `kubectl`/GitOps 天然贴合，适合"同一套底座在不同环境做小差异"。**反模式**：把所有差异都用 Helm values 表达，最后 values 文件变成几百行的 if-else 迷宫；或者用 Kustomize 做复杂逻辑（它没有条件和循环）。落地上更推荐：**Helm 出 Chart，环境差异用 values + Kustomize 叠加**，全部纳入 GitOps。

**Q16. 灰度 / 滚动 / 蓝绿 / 回滚怎么做？**

- **参考回答**：①**滚动更新**是默认，适合无状态服务，要点是 `maxSurge/maxUnavailable` 与**就绪探针必须真实反映可用**（推理服务要等模型加载 + 预热完成）；②**蓝绿**适合"版本切换必须原子、回滚必须秒级"的场景，代价是**双倍资源**——对 GPU 服务双倍成本往往不可接受，所以推理服务更常用"同池多版本 + 网关切流"；③**灰度（金丝雀）**是 AI 场景最实用的：按百分比或租户切流，观察**业务指标**（不是只看 CPU），异常自动回滚；④**回滚**的关键前置条件是**旧版本仍在位**（热实例未被销毁），否则要重新加载权重，RTO 会从秒级变成分钟级；⑤所有发布都要**冻结窗口 + 变更审计 + 一键回退按钮**。

### D. GPU / AI Infra

**★Q17. GPU 资源池与任务调度机制怎么设计？**

- **参考回答**：先按"负载特征"分池，再设计调度。①**池化维度**：推理池（在线、延迟敏感、常驻）、微调池（离线、可被抢占、长任务）、图像视频生成池（突发、显存抖动大）、开发池（小卡/共享卡）；②**调度维度**：卡型 + 互联 + 显存大小 + 优先级 + 配额；③**隔离**：不同池物理隔离（不同节点池/命名空间），避免离线任务抢占在线任务；④**排队与抢占**：在线任务优先，离线任务可被抢占（需能保存 Checkpoint）；⑤**配额与计费**：按团队/项目给 GPU 配额，并记录实际占用时长用于成本分摊；⑥**利用率治理**：监控"申请但未使用"的空占、碎片（有卡但放不下大作业）、以及空闲回收。核心判断标准是 **"大作业能不能被调度进去"** 与 **"在线 SLO 会不会被离线任务影响"**——这两个问题回答了，池化设计基本就对了。

**Q18. 什么时候真的需要多 GPU / 多节点推理？**

- **参考回答**：只有三种情况值得付这个代价：①**单卡/单机放不下模型**（显存硬约束，必须跨卡甚至跨机）；②**单请求延迟要求极高**，需要用 TP 把单层计算并行摊薄；③**吞吐优先且模型很大**，用多副本 + 路由比强行并行更划算时——注意这种是"多副本"不是"多卡切分"，两者完全不同。反过来说：**能用多副本解决的，不要用模型并行**。因为模型并行的代价是持续的跨卡/跨机通信，会吃掉算力（尤其跨机走 RoCE 时），而多副本只是复制。**关键铁律**：高频小包的并行维度（如注意力层 TP）**必须留在机内或超节点域内**，跨机只承载周期性、可预测的大流量（如专家层 EP 的 all-to-all）——这一条在第 17 章有完整推导。

**★Q19. 模型加载、缓存、冷启动、显存回收、OOM 怎么处理？**

- **参考回答**：这是一组因果关系：**冷启动慢 → 不敢缩容 → 成本高；显存管理差 → OOM → 服务不可用**。拆开处理：①**权重缓存**：把模型权重放在本地 NVMe/共享存储并做节点级缓存，避免每个 Pod 重新下载几十 GB；②**预热**：新副本必须"加载完成 + 预热推理通过"才算 Ready，否则会把流量打到未就绪实例上导致超时；③**热备池**：按流量预测保留一部分热实例，应对突发（这是响应时间从分钟降到秒的关键）；④**显存水位管理**：监控 KV Cache 使用率、碎片率、请求排队数，**在接近 OOM 之前就限流/降级**，而不是等崩；⑤**OOM 处理**：区分"单请求超长上下文"与"整体并发过高"，前者限制 max_len 或路由到长上下文专用池，后者降并发或扩容；⑥**优雅退出**：缩容/发布时先停止接新请求、等在途请求结束再释放显存；⑦**回收验证**：每次 kill GPU 任务后必须确认显存真正归还（有驱动的释放延迟与泄漏问题）。

**★Q20. FP16 / BF16 / FP8 / INT8 / INT4 怎么选？**

- **参考回答**：这是**精度—显存—吞吐—成本**的四角权衡，选择顺序是"先看硬件支持，再看精度要求，最后看收益"。①**BF16** 是训练与推理的默认选择（动态范围大、不易溢出），如果硬件支持就优先；②**FP16** 与 BF16 精度接近但动态范围小，长序列容易溢出，需要 loss scaling 保护；③**FP8**（E4M3/E5M2）是新一代硬件（H100/B200 及之后的加速卡）的主力，显存与带宽收益明显，**是目前性价比最高的一档**，但要验证业务精度；④**INT8/INT4** 收益最大（量化压缩 2–4 倍），但**对精度敏感的任务风险高**，通常用于成本优先的非核心场景，且必须做过评测对比；⑤选型方法论：**固定一个评测集，对每档量化做"质量 + 延迟 + 吞吐 + 显存"四维对比，再决定**；不要凭经验拍板，因为不同模型、不同任务的量化敏感性差异很大。补充一条：**KV Cache 的量化是独立的优化项**，常常比权重量化收益更大且风险更低。

**Q21. vLLM / SGLang / TensorRT-LLM / Triton 怎么选？**

- **参考回答**：按"你要什么"来选。①**vLLM**：生态最广、上手最快、Continuous Batching + PagedAttention 成熟，是**通用首选**，社区迭代快，与 K8s 生态集成好；②**SGLang**：RadixAttention 在**前缀共享密集**的场景（多轮对话、Agent、RAG 复用 system prompt）优势明显，复杂控制流支持好；③**TensorRT-LLM**：NVIDIA 深度优化、编译式，**极限性能与延迟最好**，代价是构建复杂、升级与调试成本高、对新模型的支持有滞后；④**Triton Inference Server**：是**多模型/多框架的服务化平台**（不仅 LLM），适合需要统一托管多种模型（LLM + CV + 传统 ML）的企业环境。落地建议：**先用 vLLM 跑通并建立基线，再用真实 workload 对比 SGLang/TensorRT-LLM，最后决定是否值得为极限性能付出运维成本**；不要在没跑通前就选最复杂的方案。抽象层上要留一个**推理后端接口**，让引擎可替换。

**Q22. ComfyUI / Diffusers 图像视频生成任务的 GPU 调度有什么难点？**

- **参考回答**：这类负载与 LLM 的差异很大：①**时长跨度大**：一张图几秒、一段视频几分钟到几十分钟，队列设计必须能**区分长短任务**，否则长任务会堵死短任务；②**显存抖动剧烈**：不同分辨率/步数/模型组合显存差异极大，容易 OOM，需要按工作流预声明资源；③**模型切换频繁**：ComfyUI 工作流可能同时用多个大模型（base + LoRA + ControlNet + VAE），切换模型有加载开销 → 要做**模型常驻/分组调度**（把常用模型组合固定在同一批节点上）；④**产物大**：图片/视频必须直接写对象存储，不能过 API 内存；⑤**同步等待不行**：必须异步任务 + 进度回调 + 可取消；⑥**成本敏感**：单任务成本差异极大，需要按分辨率/时长计费与配额。总结成一句话：**LLM 调度关心"并发与显存"，图像视频调度更关心"任务时长分布 + 模型组合 + 产物落盘"**。

### E. CI/CD & DevOps

**★Q23. 设计一条完整的 AI 系统 CI/CD 流水线。**

- **参考回答**：按 JD 给的链路逐段展开，每段都要有**产物**和**门禁**：

```
Git push → Lint/单测 → 构建镜像 → 镜像扫描/签名 → 推送 Registry →
部署到 Dev（自动） → 集成测试/评测 → 部署到 Staging（自动） →
评测门禁（质量/成本/延迟/安全） → 灰度到 Prod（手动审批） → 自动观测 → 回滚/前进
```

- 关键设计点：①**流水线即代码**（YAML 进 Git），可审计可复用；②**镜像不可变**（用 commit sha/digest 做 tag，禁用 latest），保证"所测即所发"；③**评测门禁**：AI 系统特有的环节——不只跑单测，还要跑**模型/Prompt 评测集**，指标劣化就阻断；④**多环境用同一镜像 + 不同配置**，避免"测的和发的不是一个东西"；⑤**灰度要有自动回滚**：观测窗口内错误率/延迟/成本任一劣化超阈值自动回退；⑥**制品与模型分离**：镜像走 Registry，模型走模型仓库，二者用版本号关联。
- 与普通业务的差异：**发布的不只是代码，还有模型、Prompt、Workflow**，所以门禁要多一层、回滚要快一层。

**Q24. GitOps（Argo CD）和 Gitea Actions 怎么结合？**

- **参考回答**：分工非常清楚——**CI 负责"产出并验证制品"，CD 负责"让集群状态收敛到 Git 描述的期望状态"**。①**Gitea Actions 做 CI**：提交触发 lint/单测/构建/评测，产出镜像并推 Registry，然后把新版本的 values/镜像 tag **提交到部署仓库**（这一步是关键，不是直接 deploy）；②**Argo CD 做 CD**：监听部署仓库，发现期望状态变化后自动同步到集群，并持续做**漂移检测**（谁手动改了集群会被自动纠偏或告警）；③**审批**：生产发布通过 PR Review 或 Argo 的手动 Sync 门控；④**回滚**：`git revert` 一次提交即可，比"再跑一次流水线"更快更可靠。这套组合的最大价值是**"集群里跑的东西一定有对应的 Git 记录"**，满足审计要求。

**Q25. Docker 镜像怎么做优化？**

- **参考回答**：①**多阶段构建**：编译环境与运行环境分离，产物只带运行时依赖；②**精简基础镜像**：`distroless`/`alpine`/`slim`（注意 CUDA 镜像必须与驱动匹配，Python 生态在 musl 上可能有坑）；③**层缓存**：把变化频率低的依赖放前面（先拷 requirements 再装，最后拷代码）；④**合并 RUN 并清理缓存**（`rm -rf /var/lib/apt/lists/*`、pip 的 `--no-cache-dir`）；⑤**非 root 运行 + 固定 UID**（安全合规与挂载权限都要求）；⑥**`.dockerignore`** 排除数据集、模型权重、`.git`；⑦**镜像体积直接影响冷启动**——尤其 GPU 镜像动辄十几 GB，拉取时间要算进扩容时间预算。⑧ 结合安全：**镜像扫描 + 签名 + 只允许从可信 Registry 拉取**。

**★Q26. 代码、镜像、配置、模型、Workflow 五类版本追踪怎么做？模型发布为什么不能等同于代码发布？**

- **参考回答**：①**统一"发布单元"概念**：一次发布 = `代码 commit + 镜像 digest + 配置版本 + 模型版本 + Prompt/Workflow 版本`，用一个发布 ID 串起来，能在一次查询中还原"当时线上到底是什么"；②**各自有仓库与版本号**：代码进 Git，镜像进 Registry（不可变 tag），配置进配置仓库（GitOps），模型进模型仓库（带 hash 与元数据），Workflow/Prompt 进资产库并纳入评测；③**关联关系用元数据而非人工记忆**：镜像里写入模型版本引用，或由发布系统生成映射表。
- **为什么模型发布 ≠ 代码发布**：①**体积与时长**：代码镜像几百 MB，模型几十到几百 GB，加载需要几十秒到几分钟；②**原子性**：代码可以秒级原子替换，模型做不到，必须"新副本起来再切流"；③**回滚成本**：代码回滚是换个镜像，模型回滚需要旧版本**仍在位**（热实例），否则要重新加载；④**验证方式**：代码靠单测，模型要靠**评测集 + 线上指标**；⑤**不可逆性**：某些模型/量化格式一旦升级，缓存与产物可能需要重建。所以模型必须走**独立的发布通道**：预热 → 灰度 → 观测 → 全量，并永远保留快速回退路径。

### F. 云计算架构

**Q27. VPC / Subnet / NAT / LB / 安全组 / DNS 的设计要点？**

- **参考回答**：①**分层子网**：公有子网只放 LB/NAT/堡垒机，应用与数据库放私有子网，GPU 节点默认不出公网；②**可用区**：关键组件至少跨两三个可用区，但要评估**跨 AZ 流量费用**与延迟（GPU 分布式训练跨 AZ 通常不可接受）；③**NAT 网关**：注意单 NAT 的带宽上限会成为瓶颈，且**NAT 是有成本的**（按流量计费），大流量场景要走 VPC Endpoint/PrivateLink 直连对象存储；④**安全组**：默认拒绝、按角色开端口，禁止 `0.0.0.0/0` 全开；⑤**LB**：区分四层（TCP，用于 gRPC/长连接）与七层（HTTP，用于网关），并注意**长连接与空闲超时需要与上游一致**，否则会出现随机的连接重置；⑥**DNS**：内部服务发现优先用集群 DNS/服务网格，跨 VPC 用 Private Hosted Zone，并规划好 TTL 以便故障切换；⑦**出口 IP**：调用外部模型 API 常需要固定出口 IP 加白名单。

**Q28. 跨区域 / 多云架构怎么设计？**

- **参考回答**：先问**为什么跨**——①合规（数据不能出境）；②容灾（区域级故障）；③算力获取（GPU 在某区域才有货或更便宜）。三条动因对应三种设计：合规→**数据分区 + 就近服务**，每个区域独立闭环；容灾→**主备或双活**，明确 RPO/RTO，并把"DNS/流量调度 + 数据复制"设计成套；算力→**统一调度层**，把多云 GPU 抽象成统一资源池。统一层的技术要点：①**统一控制面**（一处下发、多云执行）；②**统一身份**（IAM 联邦，避免多套账号）；③**统一可观测**（指标/日志/链路跨云汇聚）；④**网络互通**（专线/VPN + 统一 DNS/服务发现）；⑤**数据一致性**（对象存储跨区复制、模型分发策略）。**最常见的失败模式**是"只在多云各部署一套，但没有统一控制面与统一可观测"，最后运维成本翻倍却没换来可用性提升。

**★Q29. AI GPU 业务的云成本优化怎么做？**

- **参考回答**：六个抓手，按收益排序：①**提高利用率**（最大收益）：消灭空占 GPUs、碎片整理、多租户共享、把开发/测试也压到同一池子里错峰；②**用对计费模式**：稳定负载用**预留/包年**，可中断负载（微调、批处理、图像视频生成）用 **Spot/抢占式**，突发用按量；③**自动回收**：给所有 GPU 资源打标签，设定空闲 N 分钟自动停机，非工作时段自动缩容；④**存储与流量**：模型/数据集放对象存储并走**内网 Endpoint**（避免 NAT 流量费），减少跨区传输；⑤**降本技术手段**：量化（FP8/INT8）、前缀/结果缓存、批处理合并、换更合适的小模型、按需卸载；⑥**成本可见性**：按团队/项目/任务打标并出账单看板，**没有可见性就没有优化动力**。
- 一句经验：**GPU 成本的大头永远是"闲置与低利用率"**，不是单价。先把利用率做上去，再谈单价谈判。

**Q30. 混合云（本地 GPU + 云 GPU）架构的难点在哪？**

- **参考回答**：四个难点。①**数据引力**：训练数据在本地时，云 GPU 拉数据慢且贵；需要评估"数据上云"还是"模型下沉"；②**网络**：本地↔云需要专线/VPN，带宽与延迟决定了哪些任务可跨云（通常是**可离线的批任务**，不是在线推理和紧耦合训练）；③**调度统一**：需要一个能跨"本地 K8s 集群 + 云托管 K8s"的统一调度与配额视图，否则会变成两套独立系统；④**一致性与安全**：镜像/模型/Prompt 的版本要在两侧一致，身份与密钥要统一管理，数据出境要合规。适用的典型模式：**在线推理与训练放本地（数据不出域），弹性爆发与离线批处理放云**。不适用的情况：需要**紧耦合的多机分布式训练**跨云——网络条件几乎不可能满足。

### G. 可观测性与稳定性

**★Q31. Metrics + Logs + Traces + Alerts 体系怎么建？OpenTelemetry 落地要点？**

- **参考回答**：四件套各司其职：**Metrics** 看趋势与告警（Prometheus + Grafana），**Logs** 看细节（Loki/ELK，必须结构化 + 带 trace_id），**Traces** 看路径（Tempo/Jaeger，定位"慢在哪一跳"），**Alerts** 驱动人（基于 SLO 燃烧率，而不是单点阈值）。
- AI 系统的特别之处：一次请求会横跨**网关 → 编排 → 模型服务 → GPU**，所以必须用 **OpenTelemetry 的 GenAI 语义约定**统一埋点：span 里带 model 名、token 数、prompt/completion 摘要（脱敏）、工具调用、流式首字延迟（TTFT）、每 token 延迟（TPOT）。
- 落地要点：①**trace_id 全链路透传**，日志里必须带；②**采样策略**要分层：错误与慢请求 100% 采样，正常请求按比例；③**不要把 prompt/response 明文写进日志**（合规风险），要脱敏或存独立受控存储；④**指标命名统一**，否则同一个概念会有十种写法；⑤**告警分级**（P0 打断人，P1 工作时间处理，P2 只看板），并且每条告警都要有 Runbook 链接；⑥**前端体验也要观测**（白屏率、首字时间），否则后端指标好看但用户体感很差。

**★Q32. AI 系统必须建哪些业务指标？**

- **参考回答**：JD 列的清单可以直接分成四组，每组回答一个管理问题：

| 分组 | 指标 | 回答的问题 |
|---|---|---|
| **服务质量** | API 请求耗时（P50/P95/P99）、TTFT、TPOT、模型成功率、Agent Task 成功率、Workflow 执行时间 | 用户体感好不好？ |
| **成本** | Token 消耗（输入/输出）、单任务成本、单千 token 成本、每张图/每分钟视频成本 | 钱花在哪？贵不贵？ |
| **资源** | GPU 利用率（SM/显存带宽）、显存占用与水位、Queue Length、并发数、模型推理耗时 | 容量够不够？要不要扩？ |
| **稳定性** | 错误率与错误码分布、超时率、重试率、熔断触发次数、降级次数、可用性（SLO 达成率） | 稳不稳？哪里在劣化？ |

- 建指标的三个原则：①**每个指标都要有"看到它之后要做什么"**，否则是噪音；②**能下钻**（按租户/模型/版本/节点维度切分）；③**能关联**（成本和版本关联、成功率和模型版本关联），否则出了问题只能猜。

**Q33. 线上故障怎么定位？容量规划怎么做？**

- **参考回答**：**定位**用"先切分、再下钻"：①**切分**：按时间（突变/渐变）、按影响面（全部/局部）、按维度（模型版本/节点/可用区/租户）—— 切分的结果直接指向根因类型；②**下钻**：网关 → 编排 → 模型服务 → GPU/网络，逐层看"这一层的延迟/错误，是它产生的，还是上游传下来的"；③**判定技巧**：全部副本一起劣化 → 多半是上游输入变化或依赖故障；只有部分副本 → 多半是硬件/节点/版本问题；④**保留证据**：指标快照 + 链路 + 日志，事后必须能复盘。
- **容量规划**：①**建模**：容量 = 单副本可承载并发 × 副本数，而单副本容量由 **显存 / 单请求 KV 占用** 决定，后者随上下文长度线性增长，所以要**按长度分布而不是平均值**算；②**预测**：日/周周期 + 增长趋势 + 大促/活动系数；③**留冗余**：P95 峰值 × 1.3 以上，并明确"超载时的降级顺序"；④**验证**：定期压测校准，因为模型/引擎升级会改变单副本容量；⑤**扩容分级**：先限流与降级 → 再加副本 → 最后加卡/加池，因为三者的响应时间和成本完全不同。

## 7. 系统设计大题（架构师必考）

### 7.1 设计一个企业级 AI 平台（支撑 AIGC 图像/视频 + LLM 多模型 + Agent）

**题目**：公司要建一个统一 AI 平台，业务方包括：客服知识助手、代码助手、营销图生成、短视频生成。要求对接多家外部模型和自建 GPU 集群，支持多租户、成本可控、可灰度、可回滚。请给出架构设计与关键取舍。

**参考架构（分层回答）**：

```
接入层   统一 API / SDK / 控制台 │ 鉴权、租户、配额、审计
─────────────────────────────────────────────────────
网关层   AI Gateway（Go）
         协议归一 · 模型路由 · Fallback · 限流/熔断/重试 · 流式转发 · 成本打点
─────────────────────────────────────────────────────
编排层   Workflow / Agent Runtime（Python）

─────────────────────────────────────────────────────
模型层   统一模型调用层
         外部模型 Adapter（OpenAI/Claude/Gemini/DeepSeek/Qwen/MiniMax）
         自建推理服务（vLLM/SGLang/Triton）· 多副本 · 前缀缓存 · 量化
─────────────────────────────────────────────────────
算力层   GPU 资源池（K8s）
         推理池 / 训练微调池 / 图像视频池 / 开发池 · 卡型分池 · 拓扑感知调度
─────────────────────────────────────────────────────
数据层   对象存储（模型/数据集/产物）· 元数据库 · 向量库 · 缓存 · 消息队列
─────────────────────────────────────────────────────
工程层   CI/CD + GitOps（Gitea Actions → Harbor → Argo CD）
         五类版本追踪：代码/镜像/配置/模型/Workflow
─────────────────────────────────────────────────────
观测层   OTel + Prometheus + Loki + Tempo + Grafana + 告警
```

**关键取舍（面试官真正想听的）**：

1. **自建 vs 外采**：外部模型快、无算力投入，但成本随量线性增长且数据出域；自建推理成本固定、数据可控，但利用率和运维是负担。**建议混合**：核心/敏感业务自建，长尾/弹性需求走外部；并在网关层做到"切换只改配置"。
2. **单集群 vs 多集群**：先用少而大的集群（运维简单），按爆炸半径与合规要求再拆；不要一上来就多集群。
3. **Agent 复杂度**：**单 Agent 优先**，只在"上下文压力"与"交叉验证"两个场景引入多 Agent；拓扑越简单越好。
4. **调度粒度**：整卡调度简单可靠，MIG/共享适合开发与小模型，**不要用共享卡跑大模型推理**。
5. **一致性 vs 可用性**：配额、计费、审批必须强一致（谁批的、花了多少）；对话历史、缓存可以最终一致。
6. **不能省的**：限流降级、成本可见性、版本追踪、灰度回滚。**可以后置的**：多集群、服务网格、多云统一调度、复杂的自愈体系。

**度量（收尾必须有）**：平台级 SLO（可用性、P99 延迟）、业务指标（任务成功率、TTFT）、成本指标（单任务成本、GPU 利用率）、治理指标（配额达成率、发布回滚率）。

### 7.2 故障题：GPU 节点批量 OOM + 模型成功率下降

**题目**：早高峰 9:10，监控报警：某推理池 30% 节点出现 GPU OOM，模型成功率从 99.8% 掉到 96%，P99 延迟翻倍。你作为架构负责人，怎么处理？

**参考回答（分"止血—定位—修复—预防"四段）**：

1. **止血（0–10 分钟，优先于找根因）**：①确认影响面（哪些模型、哪些业务、多少用户）；②立即**收紧输入**（限制最大上下文长度与最大并发），把压力降下来；③**摘除 OOM 节点**，把流量切到健康副本；④如仍不足，**启用降级**（换小模型 / 排队 / 提高前缀缓存命中）；⑤通知业务方与客服，准备好话术。
2. **定位（并行进行）**：①按维度切分——只在部分节点？只在某个模型？只在特定输入长度？②查"变量"：昨晚到今天有没有**发布**（模型版本、Prompt、代码、配置）、有没有**流量结构变化**（长上下文请求比例、图像任务混入）、有没有**基础设施变化**（驱动升级、节点替换）；③看**时间相关性**：如果是"9:00 开始"，很可能与早高峰流量结构（长上下文/并发）相关；如果是"9:10 突然"，优先怀疑发布或依赖故障；④核对 **KV Cache 水位**与**排队长度**曲线，判断是"容量不足"还是"单请求过大"。
3. **修复**：①若根因是流量结构变化 → 调整容量模型与限流参数（按长度分桶限流，而不是总量限流）；②若是发布引入 → **回滚**（这也是为什么要求旧版本保持热实例）；③若是显存泄漏/碎片 → 重启相关副本并升级驱动/引擎版本，同时加入定期巡检；④修复后**用同一批流量验证**指标回到基线。
4. **预防（必须落到机制）**：①把"按上下文长度分桶的容量模型"写进容量规划；②增加**OOM 前兆告警**（KV 水位 + 排队长度趋势），而不是等 OOM 才报；③把"发布窗口冻结在早高峰前"变成制度；④补充故障演练场景（长上下文突增、模型版本回滚）；⑤复盘输出 Runbook 与责任项。
