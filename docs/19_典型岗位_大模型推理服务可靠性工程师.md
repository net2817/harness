# 典型岗位与面试：大模型推理服务可靠性工程师（LLM Inference SRE）

> 本章把一则真实岗位 JD（大模型推理服务可靠性工程师）拆解为**岗位定位 → 职责解读 → 任职要求 → 能力地图 → 模拟面试问答**，作为前面章节知识的"就业出口"。所有问题都按 JD 原文要求设计，回答尽量给到可直接复述的工程口径。

## 1. 岗位定位（原文）

负责 LLM 推理服务全链路的稳定性，让**模型、框架、Router、网关**等每个环节都处于**可控、可观测、可回滚、可恢复、可容灾**的状态；通过持续容灾演练和自研工具/系统，持续提升推理系统的可靠性与运维效率。

**一句话拆解**：这不是"运维 GPU"的岗位，而是**推理链路的 SRE**。核心对象是"一次推理请求从网关进来、经 Router、Runtime、GPU/NCCL，再返回"的整条链路；核心交付是 **SLO 达标 + MTTR 下降 + 自动化率上升**。

## 5. 模拟面试问答（24 题）

> 建议用法：先自己答一遍，再对照"参考回答"补齐缺口。加 ★ 的是高频必考。

### A. SLO 与发布稳定性

**★Q1. TTFT 和 TPOT 分别是什么？你这个岗位要对它们负责，你会怎么定 SLO？**

- **考点**：是否真懂推理指标，还是只会抄名词。
- **参考回答**：TTFT（Time To First Token）= 首 token 延迟，主要由 **Prefill** 阶段决定，受输入长度、批大小、算力影响；TPOT（Time Per Output Token）= 相邻输出 token 的间隔，由 **Decode** 阶段决定，**受显存带宽限制**（每步要读一遍权重），因此与算力关系不大。定 SLO 的分层做法：①按业务分级 —— 交互式（TTFT P99 ≤ 1 s）、批量/异步（TTFT 可放宽到数秒）；②按输入长度分桶 —— 8K 和 128K 上下文不能共用一个阈值；③**同时约束 TTFT、TPOT 和成功率**，并区分 P50/P95/P99；④成功率必须和延迟一起看，否则"快速失败"会掩盖真实可用性。补充一个易错点：单流 TPOT 的上界由"单卡权重 ÷ 显存带宽"决定，**加卡不能降低单流 TPOT**，只能提高并发吞吐——这是设计 SLO 时最容易搞错的地方。

**★Q2. 推理服务的灰度发布怎么做？模型版本、框架版本升级如何保证可回滚？**

- **参考回答**：四层都要能灰度、能回滚：**网关**（权重/路由规则）→ **Router**（流量分配策略）→ **Runtime**（推理引擎 + 模型版本）→ **框架/驱动**。做法：①**新版本先起影子/小流量**，按 1% → 5% → 25% → 100% 分档，每档观察 TTFT/TPOT/成功率/GPU 利用率；②**模型与框架升级解耦**，不要一次同时升级引擎和权重；③**回滚要"一键且幂等"**：镜像/权重版本化（immutable tag，禁止 latest）、Router 支持秒级切回旧池、网关保留旧上游；④**回滚前置条件**：旧版本实例保持热备（不被销毁），否则回滚要重新加载几十 GB 权重，RTO 会很长；⑤升级窗口内**冻结其他变更**，避免多因故障。

**Q3. 如何设计推理服务的可用性指标与错误预算？**

- **参考回答**：可用性口径用**成功率**而非"进程存活"：`成功率 = 返回合法结果的请求 / 合法请求总数`，把 4xx 客户端错误、超时截断、空响应都明确归类。SLO 示例：月成功率 ≥ 99.9%，TTFT P99 ≤ 1 s，TPOT P99 ≤ 50 ms。**错误预算 = 1 − SLO**，按月滚动：99.9% → 月预算约 43 分钟。预算健康时允许发布和演练；**预算烧速过快（burn rate）触发告警**，用多窗口（1h 快烧 + 6h/3d 慢烧）双阈值，避免单点抖动刷屏。预算耗尽时**冻结非必要变更**，把人力转向可靠性修复和复盘。

### B. 全链路可观测（核心考点）

**★Q4. 让你从"推理、网络、Workload"三个维度建黄金指标，你分别埋什么？**

- **参考回答**：
  - **推理维度**：QPS/并发数、TTFT、TPOT、E2E 延迟、成功率/错误码分布、队列长度与排队时延、KV Cache 命中率与水位、批大小分布、单副本吞吐。
  - **网络维度**：网关 5xx/超时率、上游连接数与连接复用率、TCP 重传、RDMA 丢包/重传、PFC 触发次数、跨 AZ 时延、带宽利用率。
  - **Workload（GPU/运行时）维度**：GPU 利用率（SM/显存带宽）、显存占用与 OOM 次数、NCCL 通信耗时与超时、慢卡标记、温度与降频、CUDA/驱动错误。
  - 关键原则：**每个指标都能对应一个"可行动的处置动作"**，否则不要放上首页。首页只放 RED（Rate/Error/Duration）+ 资源水位，细节通过下钻看。

**★Q5. 线上反馈"推理变慢"，你怎么从网关 → Router → Runtime → GPU/NCCL 逐层下钻？**

- **参考回答**：按**链路顺序排除，每层只问两个问题："这一层是不是瓶颈"和"这一层的输入是否已经变慢"**：
  1. **网关**：先看入口 QPS、连接数、5xx、超时率 —— 如果网关侧延迟就高，先排除限流、TLS 握手、连接耗尽、后端健康检查误杀。
  2. **Router**：看路由决策耗时、队列排队时间、各上游权重与实例分布 —— 常见问题是**流量倾斜**（某副本被打爆）或**长连接粘滞**导致新实例没流量。
  3. **Runtime**：看排队 vs 计算耗时占比 —— 用"排队时延 / 批处理时延 / 生成时延"三段拆解。排队高 = 容量不足或路由不均；生成慢 = 模型/显存问题。
  4. **GPU/NCCL**：看 SM 利用率、显存带宽、显存水位、是否降频，以及 NCCL 集合通信耗时/超时。
  - **判定技巧**：如果**只有某几个副本慢** → 大概率 GPU/慢卡/降频；如果**全部副本一起慢** → 大概率上游输入变长（如上下文变长导致 TTFT 上升）或网络/存储侧问题。**先看"变慢的分布"，再看单点**，能省一半时间。

**Q6. 没有业务日志的情况下，你怎么判断是网络问题还是 GPU 问题？**

- **参考回答**：用"**换维度对照**"法：①**换节点**：把同一流量导到另一组节点，如果恢复 → 原节点硬件/驱动问题；②**换模型**：换一个小模型跑同一流量，如果仍然慢 → 偏网络/平台；③**看时间形态**：网络抖动通常表现为**周期性毛刺、重传、超时堆积**，GPU 问题通常表现为**持续偏高、单卡异常、OOM/NCCL 超时**；④**看相关性**：把网络指标与延迟曲线叠加，网络先动 = 网络；GPU 指标先动 = GPU。最后一定**留证据**（指标截图、时间线）写进 Postmortem。

### C. On-call 与故障处理

**★Q7. P0 故障时你作为 IC（Incident Commander）的处置流程？**

- **参考回答**：IC **不亲自查故障**，职责是"控场 + 决策 + 沟通"：
  1. **确认与分级**（0–2 min）：确认影响面（哪些业务、多少用户、有无资损），定 P0/P1；
  2. **拉起作战室**：指定 **Ops（操作）**、**Comms（对外沟通）**、**Scribe（记录时间线）**，明确"未经 IC 同意不做高风险操作"；
  3. **止血优先于根因**：允许"粗暴但有效"的动作 —— 切流、回滚、限流、降级、重启、扩容；把根因留给恢复后；
  4. **定期同步**：每 15 分钟对外同步一次状态（已影响 / 已尝试 / 下一步），避免信息真空；
  5. **恢复确认**：用成功率、TTFT/TPOT、错误率**三项同时回到基线**才算恢复，不靠"感觉好了"；
  6. **收尾**：保留现场（日志、指标快照、core dump），**48–72 小时内出 Postmortem**。
  - 补充：P0 期间**禁止做没有回滚预案的操作**，"求稳不求快"。

**★Q8. 如何系统性压降 MTTR？**

- **参考回答**：把 MTTR 拆成 **MTTD（发现）+ MTTA（响应）+ MTTR-R（定位）+ MTTR-F（止血/恢复）** 四段，分别打：
  - **降低 MTTD**：SLO 燃烧率告警替代静态阈值，多窗口双阈值减少误报漏报；业务级"黑盒拨测"补足内部指标盲区。
  - **降低 MTTA**：告警直接带"首查 Runbook 链接"和"影响面预估"，让值班人不用先想"该看哪个看板"。
  - **降低定位时间**：**预置诊断树 + 一键下钻看板**，把常见故障的定位路径固化；建设故障案例库，同类问题第二次要快。
  - **降低恢复时间**：**一键切流/回滚/扩容**，把恢复动作从"人肉操作 10 分钟"压到"点一下 30 秒"；预备容量与热备实例。
  - **度量**：每次复盘都记录四段耗时，看哪一段最长就优化哪一段——通常**定位时间占比最大**。

**Q9. 典型案例：某天推理成功率从 99.9% 掉到 97%，你怎么办？**

- **参考回答**：先**分维度切分**再动手：①按**错误码**切（超时 / 5xx / 空响应 / 无效结果）；②按**时间**切（突变还是缓降）；③按**副本/节点/AZ**切（全部还是局部）；④按**输入**切（长上下文？某类请求？）。假设切出来是"超时为主 + 集中在某 AZ"，则优先怀疑该 AZ 的网络/资源；若是"全部副本、错误码以 OOM 为主"，则怀疑上下文变长或并发上涨导致显存不足。**止血动作**：先切走故障 AZ 流量 + 限制最大并发/最大输入长度，再定位。事后必须回答"为什么没被提前发现"（告警覆盖缺口）并补上。

### D. 容灾演练

**★Q10. 多 AZ 故障转移演练怎么设计？怎么证明"无损"？**

- **参考回答**：**分层设计**：①**单元级**：单 Pod/单节点 kill，验证 K8s 自愈；②**副本级**：摘除一个推理副本，验证 Router 重路由；③**AZ 级**：整个 AZ 摘除，验证容量是否够（**关键：剩余 AZ 必须能承接全部流量**，否则就是"伪容灾"）；④**依赖级**：存储、网关、DNS、鉴权等公共依赖故障。**"无损"的证明**：演练前先设**量化判据**——成功率不低于基线 −0.1%、TTFT P99 不劣化 >20%、无用户可见错误、无数据丢失；用**灰度流量**或**影子演练**降低风险。演练后输出：**发现清单 + 责任方 + 截止时间 + 复测结果**，缺陷不闭环不算完成。

**Q11. 故障注入如何覆盖 GPU/NCCL/网关/Router？**

- **参考回答**：按层准备"注入手段库"：
  - **GPU**：显存占满（模拟 OOM）、降频（功耗/温度）、ECC 错误、掉卡；
  - **NCCL**：注入通信延迟/丢包、单卡 hang、集合通信超时；
  - **网关**：注入 5xx、超时、连接重置、限流；
  - **Router**：摘实例、改权重、放大路由延迟；
  - **K8s 层**：Pod kill、节点 NotReady、网络分区、DNS 故障。
  - 原则：**注入必须可控制、可观测、可回滚**，并且**只在演练环境或受控灰度**执行；每次注入都要有明确的"预期表现"和"失败判据"。工具上可用 Chaos Mesh / ChaosBlade + 自研注入平台，接入 CI 做常态化演练。

**Q12. 演练发现的韧性缺陷怎么闭环？**

- **参考回答**：**三件套**：①**缺陷单**（描述现象、复现步骤、影响面、期望行为）；②**验收标准**（下次演练的通过判据，必须是可测的）；③**回归演练**（固定周期自动重跑，不能"改完就算完"）。治理上把缺陷分三类：**架构级**（需要改设计，排期长）、**配置级**（马上改）、**流程级**（改 Runbook/告警）。用**韧性看板**跟踪"发现数 / 闭环数 / 平均闭环时长 / 复测通过率"。

### E. 运维工具/平台开发

**★Q13. 一键切流/回滚怎么实现？如何保证幂等与安全？**

- **参考回答**：**实现**：把"切流"抽象成对 Router/网关的一次**声明式变更**（改权重或改上游池），工具只负责"下发 + 校验 + 回滚"。**幂等**：每次操作带唯一 `requestId`，服务端按 ID 去重；目标状态用"期望版本号"表达（如 `traffic_policy=v42`），重复下发同一版本不产生副作用。**安全**：①**双人确认**（高风险操作要求第二人批准）；②**预检**（切流前检查目标池健康、容量水位是否够）；③**熔断**（切流后 N 分钟内指标异常自动回滚）；④**审计**（谁、何时、改了什么、结果如何全部留痕）；⑤**干跑（dry-run）**先输出"将要发生的变更"。高危动作永远保留"人工兜底"入口。

**Q14. 自动巡检与自愈规则怎么设计？如何避免误操作？**

- **参考回答**：**分级自治**：L0 只读巡检（生成报告）→ L1 自动告警 → L2 自动执行低风险动作（重启卡死 Pod、摘除不健康副本）→ L3 自动执行高风险动作（切流、扩缩容，需审批或强校验）。**规则设计**：每条自愈规则必须写清"触发条件 / 动作 / 抑制条件 / 回滚条件 / 最大影响面"。**防误操作**：①**冷却期**避免反复触发；②**影响面上限**（一次最多摘 N 个副本或 M% 流量）；③**熔断开关**（自愈连续失败自动停止并转人工）；④**影子模式**先跑一段时间只记录不执行，比对"如果执行了会怎样"；⑤**全量审计 + 一键撤销**。

**Q15. 故障注入平台怎么设计？**

- **参考回答**：核心是**"实验即代码"**：①**实验定义**（目标对象、故障类型、参数、持续时间、预期表现、成功判据）；②**编排**（按场景组合多个注入，如"AO 摘除 + 数据库延迟"）；③**安全护栏**（只在指定命名空间/标签生效、最大爆炸半径、自动终止时间、紧急停止按钮）；④**观测与判定**（自动采集演练期指标，与基线对比，自动给出"通过/不通过"）；⑤**沉淀**（实验入库、定期回归、纳入发布门禁）。实现上可基于 Chaos Mesh 做执行器，自研做编排、审批与报告。

### F. 容量与水位管理

**★Q16. 如何基于流量趋势和 workload 特征做容量规划？**

- **参考回答**：三步：①**建模**：把容量换算成"**每副本能承载的并发 = KV 池大小 ÷ 单请求 KV 占用**"，再乘副本数。KV 占用随上下文长度线性增长，所以要按"**输入长度分布**"而不是平均值算；②**预测**：用历史流量的**日周期/周周期 + 增长趋势**做容量预测，并留出**峰值冗余**（如 P95 峰值 × 1.3）；③**验证**：定期**压测校准**，因为模型/框架升级、量化、批处理策略变化都会改变单副本容量。**关键认知**：推理容量瓶颈通常是**显存（KV Cache）**而不是算力，规划时必须按最长上下文算最坏情况。

**Q17. GPU 显存 / KV 缓存水位怎么监控和预警？**

- **参考回答**：监控三层：①**显存水位**（used/total，含权重、KV、激活、碎片）；②**KV Cache 水位**（已用块 / 总块数，命中率、驱逐次数、preemption 次数）；③**请求侧**（排队长度、被拒/降级请求数）。预警用**水位 + 趋势**双条件：如"KV 水位 >85% 且 15 分钟内上升 >10 个百分点"才告警，避免瞬时抖动误报。**处置动作**：限制最大并发/最大输入长度、触发扩容、把长上下文请求路由到专用池（PD 分离）、必要时降级。**不要等到 OOM 才动手**，OOM 之后再恢复要重新加载权重，恢复时间很长。

**Q18. 弹性扩缩容在推理场景的难点是什么？**

- **参考回答**：和普通无状态服务最大的区别是**冷启动极慢**：拉起一个新副本要下载几十 GB 权重 + 加载显存 + 预热（warmup），可能几分钟到十几分钟，而流量洪峰可能 1 分钟就到。因此：①**扩容要提前**（基于趋势预测 + 流量爬升斜率，而不是等 CPU/GPU 打满）；②**缩容要滞后**（保留缓冲，避免抖动反复扩缩）；③**准备热备池 / 预热实例**（镜像、权重本地缓存、共享存储按需加载）；④**扩缩容要能"分级"**：先加并发/批处理，再加副本；⑤HPA 只看 GPU 利用率往往会滞后，应结合**队列长度、TTFT 劣化**等前兆指标。

### G. Kubernetes

**★Q19. 在 K8s 上部署推理服务的关键点有哪些？HPA 有哪些局限？**

- **参考回答**：关键点：①**资源声明**用 `nvidia.com/gpu` 等 device plugin，限制 GPU/NPU 数量；②**就绪探针要反映真实可用**（模型加载完 + warmup 完成才算 Ready，否则流量会打到没准备好的实例）；③**优雅终止**（`preStop` + `terminationGracePeriodSeconds`，等在途请求处理完再退出）；④**反亲和/拓扑分布**，避免所有副本挤在同一节点/AZ；⑤**模型权重用共享存储或本地缓存**，避免每个 Pod 重复下载。**HPA 局限**：默认 HPA 看 CPU/内存，而推理瓶颈在 GPU 和 KV 显存；GPU 利用率到 100% 时其实已经饱和、再扩已晚；且**冷启动慢**导致 HPA 的扩容来不及。因此常用 **KEDA + 自定义指标（队列长度/并发数）**，并配合**预测式扩容 + 预热池**。

**★Q20. Pod 一直 Pending 或 CrashLoopBackOff，你怎么排查？**

- **参考回答**：
  - **Pending**：`kubectl describe pod` 看 Events —— 常见是**资源不足**（GPU 不够/整卡被占）、**节点选择器/污点容忍不匹配**、**PVC 未绑定**、**超出节点配额**。CPU 场景查 `kubectl top`，GPU 场景查节点可分配 GPU 数。
  - **CrashLoopBackOff**：`kubectl logs --previous` 看**上次崩溃日志**——常见是 OOMKilled（显存/内存）、模型路径挂载失败、依赖服务不可达、启动脚本报错、权限问题。
  - **经验**：先看 **Events**（时间顺序倒着看），再看 **previous 日志**，两者能解决 80% 的问题；剩下 20% 用 `kubectl exec` 进去手工复现。

**Q21. 如何用 K8s 实现推理服务的高可用与"就地重启"？**

- **参考回答**：**高可用**：副本数 ≥2（跨节点/AZ）、PDB（PodDisruptionBudget）保证滚动更新/驱逐时可用副本数、`topologySpreadConstraints` 打散、readinessProbe 摘除坏实例、Service/Ingress 前置网关做健康检查与重试。**就地重启**：如果进程挂了但容器没重启（推理引擎 hang），用 **livenessProbe** 触发容器重启；若需要"不丢 GPU 卡"的快速恢复，可用**容器内进程 supervisor 自拉起**或 **in-place restart**（K8s 1.27+ 的 ContainerRestartPolicy 或自研 Agent），避免重新调度导致排队、重新下载权重。

### H. SRE 方法论

**★Q22. SLO / 错误预算怎么落地？预算烧完了怎么办？**

- **参考回答**：落地路径：①**选对 SLI**（成功率、TTFT P99、TPOT P99）——必须与用户体感相关；②**定 SLO**（如 99.9%），并在**看板上和值班 SOP 里显式化**；③**算错误预算**（1 − SLO），**按月滚动**；④**告警用燃烧率**（1h 14.4×快烧 + 6h/3d 慢烧），而不是"错一次就报"。**预算耗尽**：冻结非必要变更（功能发布、非紧急演练），把人力聚焦到可靠性修复；已排期的可靠性工作优先执行；如果长期烧穿，说明**SLO 定得不合理或架构有系统性缺陷**，要回头修 SLO 或改架构——**不要靠"加人值守"掩盖**。

**Q23. Postmortem 怎么写？为什么强调 blameless？**

- **参考回答**：**结构**：①影响（用户/业务/时长/资损）；②时间线（分钟级，含"发现—响应—止血—恢复"）；③根因（技术根因 + 为什么没被预防）；④**做得好的地方**（不能只写问题）；⑤改进项（每条**有责任人 + 截止日期 + 优先级**，分"止血型/预防型/检测型"）。**blameless 的意义**：目的不是追责，而是让当事人**敢说真话**——如果复盘变成批斗，下次故障就没人敢如实报告，组织会失去真实信息。原则：**对事不对人**，聚焦"系统为什么允许这个错误发生"（如"为什么没有防护栏"而不是"谁手抖了"）。

### I. Python / Go 工具开发

**★Q24. 写一个"健康检查 + 自动切流"工具的完整思路（可用伪代码）**

- **考点**：是否具备"开发能力 + 可靠性意识"双重要求。
- **参考回答**：要素：**探测 → 判定 → 动作 → 熔断 → 审计**。

```python
# 伪代码：健康巡检 + 自动摘除不健康副本（保守版）
import time, requests

WINDOW, FAIL_THRESHOLD, MIN_HEALTHY = 5, 3, 0.8   # 5次采样, 连续3次失败, 至少保留80%健康
STRIKES: dict[str, int] = {}

def probe(inst):
    t0 = time.time()
    try:
        r = requests.get(f"http://{inst}/health", timeout=2)
        return r.status_code == 200 and (time.time() - t0) < 1.0
    except Exception:
        return False

def reconcile(instances, router):
    healthy = 0
    for inst in instances:
        ok = probe(inst)
        STRIKES[inst] = 0 if ok else STRIKES.get(inst, 0) + 1
        healthy += 1 if ok else 0
    if healthy / len(instances) < MIN_HEALTHY:
        audit("GLOBAL_DEGRADED", "取消本轮动作，保持现状并告警")   # 熔断：全局异常不摘流
        return
    for inst, s in STRIKES.items():
        if s >= FAIL_THRESHOLD and router.weight(inst) > 0:
            audit("DRAIN", inst, f"连续{s}次失败，摘除")           # 幂等：权重已是0则跳过
            router.set_weight(inst, 0)                            # 动作用"声明式"下发
            cooldown(inst, 300)                                   # 冷却，避免反复抖动
```

- **要点补充**：①**幂等**（已经是 0 权重就不再操作）；②**熔断**（全局异常时不做任何摘流，避免"把健康判断错误放大成全局故障"）；③**最小影响面**（保留 ≥80% 健康副本）；④**冷却期**（避免震荡）；⑤**审计**（谁在何时摘了谁，必须留痕、可一键恢复）；⑥生产上还要做**多实例选主**（避免多个巡检器同时操作）和**干跑模式**。

**★Q25. 如果要你从 0 到 1 建设这个岗位的体系，你前 90 天做什么？**

- **参考回答**（面试压轴题，考体系化思维）：
  - **第 1–30 天：看清现状（可观测）**——摸清链路（网关→Router→Runtime→GPU/NCCL）、补齐**黄金指标看板**和**分层下钻**、定义并上线**核心 SLO**、梳理 On-call 与告警质量（先消灭误报和漏报）。
  - **第 31–60 天：能控（可回滚、可恢复）**——建 **Runbook**、做**一键切流/回滚**、组织**第一次容灾演练**（先从单副本/单 AZ 开始）、建立 Postmortem 机制。
  - **第 61–90 天：能防（可容灾、自动化）**——建**故障注入平台**与常态化演练、上线**自动巡检与低风险自愈**、建**容量与水位看板**和扩缩容策略、沉淀**故障案例库**。
  - **度量**：对外汇报用四个数——**可用性（SLO 达标率）、MTTR、自动化率、演练缺陷闭环率**。

**Q26. 为什么"成功率"要和"延迟"一起看？只盯成功率会有什么问题？**

- **参考回答**：因为二者可以互相掩盖：**快速失败**（立刻返回错误或空结果）会让延迟曲线非常好看，但用户其实完全不可用；反过来，**无限制排队**能让成功率保持 100%，但延迟已经崩了。所以 SLO 必须是"**成功率 + TTFT + TPOT 同时达标**"的联合条件，并且要监控**被降级/被截断的请求占比**——把"悄悄降级"显式暴露出来，否则你会得到一个"指标好看但用户骂街"的系统。
